## Findings

### SEC-19-F25 — The dev server is open to the network and a public tunnel, and Vite 5.4.21 hands out the repo's `.env` on Windows

- Severity and confidence: P1, reproduced locally with synthetic marker
  files on a scratch Vite server bound to loopback. Whether a tunnel is or
  was running, and what the real `.env` holds, was not checked; no real
  host was probed.
- Affected entry point and source:
  [`apps/web/vite.config.ts`](../../apps/web/vite.config.ts) lines 24–27
  (`host: true`; `allowedHosts` defaulting to the two ngrok hostnames).
  Vite 5.4.21 (`apps/web` dev dependency) is in GHSA-fx2h-pf6j-xcff
  (`server.fs.deny` bypass on Windows alternate paths, fixed in 6.4.3), and
  in GHSA-rq7h-c2jc-7f22 and GHSA-4w7w-66w2-5vf9 (other file-serving
  bypasses).
- Actor, preconditions, and violated boundary: anyone who can reach the dev
  server while it runs: any machine on the same network (it binds every
  interface), and anyone on the internet while an ngrok tunnel points at it.
  The two tunnel hostnames are published in this public repository. The
  development machine is Windows. Invariant broken: engine and server
  credentials stay server-side; production-style secrets never leave the
  `.env`.
- Expected versus observed: Vite's deny list should refuse `.env`. Observed
  on the scratch server: the plain path → 403, but a Windows alternate form
  of the same path → 200 with the synthetic `.env` marker in the body; the
  same form also returned a denied `*.pem` marker. Separately, `/@fs/` served
  a synthetic `dev.db` file under `apps/server/` with no bypass at all, since
  a SQLite file is not on the deny list. A marker file outside the
  workspace → 403 both ways.
- What a real `.env` and `dev.db` hold: `.env.example` lists
  `ENGINE_TOKEN` (the engine's bearer token), `SECRET_KEY` (which decrypts
  stored engine host tokens), `RESEND_API_KEY` (sends mail as the project)
  and `POSTGRES_PASSWORD`. The development database holds email addresses of
  anyone who signed in locally, session and guest token hashes, and host
  tokens encrypted with that `SECRET_KEY`.
- Minimal synthetic reproduction and side-effect assertions: export the
  tree, put a `.env` with a unique marker at the root, start
  `vite --host 127.0.0.1` from `apps/web`, request the root `.env` under
  `/@fs/` in its plain and Windows alternate forms; assert the plain form is
  403 and that no form returns the marker. Today the alternate form returns
  it.
- Impact and affected milestones: a remote read of local secrets and
  development user data while the dev server runs. If the local `.env` ever
  held a real Resend key or any credential shared with a deployment, it may
  have been readable from the internet whenever the tunnel was up since
  2026-10-13. Every milestone, since it is the everyday dev setup.
- Proposed fix (owner's call; not made here):
  - Bind the dev server to loopback by default (`host: '127.0.0.1'`), and
    turn on network or tunnel exposure only through an explicit environment
    variable; drop the hard-coded ngrok hostnames from the committed file.
  - Upgrade Vite to 6.4.4 or later (and `@vitejs/plugin-react` to match) in
    its own change; rerun the web suite and a browser spec.
  - For a tunnel, prefer serving the built app from the server (no `/@fs/`)
    over tunnelling the dev server, and put the tunnel behind its own
    access control.
  - If a tunnel has run since 2026-10-13, treat the local `.env` values as
    exposed: rotate the engine token, `SECRET_KEY` (re-encrypting host
    tokens) and any Resend key, through the owner's own accounts.
  - Regression check: a review step that starts the dev server and asserts
    it listens on loopback only, plus the reproduction above after the
    upgrade.
- Status, owner, next action, and review date: open; owner to act before
  more feature work; recheck in a change review with the fix, by
  2026-11-16.

### SEC-14-F26 — Production with no mail key writes live sign-in links to the log

- Severity and confidence: P2, reproduced (production-mode build, synthetic
  settings, no `RESEND_API_KEY`: a link request → 200 and the log holds the
  complete sign-in URL with its token).
- Affected entry point and source:
  [`config.ts`](../../apps/server/src/config.ts) does not require
  `RESEND_API_KEY` in production; [`index.ts`](../../apps/server/src/index.ts)
  then picks `ConsoleMailer`, which prints every mail
  ([`email.ts`](../../apps/server/src/email.ts) line 22) and keeps it in its
  `sent` array for the life of the process.
- Actor, preconditions, and violated boundary: a production deploy where the
  key is missing or mistyped. Anyone who can read the platform's log can
  sign in as any person who asked for a link in the last 15 minutes. People
  asking to sign in get no email and no error. Invariant broken:
  "Production fails closed on absent credentials"; the playbook also forbids
  login query strings in logs. The memory list grows with every mail.
- Correction: the 2026-09-29 and 2026-10-13 reports called the console
  mailer development-only. That was true of intent, not of the code.
- Proposed fix: add `RESEND_API_KEY` (and a real `EMAIL_FROM`) to the
  production list in `loadConfig`; in `ConsoleMailer`, keep `sent` only when
  the test outbox is on. Regression test: `loadConfig` in production without
  the key throws.
- Status: open; next server change.

### SEC-18-F23 — Production dependencies carry newly published advisories (widened)

- Severity and confidence: P3, source-confirmed reachability.
- What: with the same lockfile as 2026-10-13, `pnpm audit --prod` now
  reports 23 advisories. Triage:
  - `@modelcontextprotocol/sdk` 1.30.0 (through `packages/engine-client`):
    seven advisories, all fixed in 1.32.0. Five concern its server
    transports, server bearer authentication or experimental tasks; the
    engine client imports only `client/index.js` and
    `client/streamableHttp.js`, so they are not reachable. GHSA-6qxp-vccf-f47h
    (OAuth client) needs an `authProvider`, which the client does not set.
    GHSA-6prh-2h8m-c8cw (client transports following cross-origin redirects)
    is the one client-side item: it matters only if the configured engine
    URL answers with a redirect to another host; the engine URL is operator
    configuration. Not reproduced.
  - `body-parser`, `express`, `qs`, `hono`, `@hono/node-server`,
    `ip-address`: dependencies of the SDK's server side; not loaded by the
    client. Not reachable.
  - `zod` 3.25.76 (GHSA-mrhx-c7xc-m3w5, memory use on oversized constrained
    collections; fixed only in zod 4.6.6): the engine client validates
    engine responses with it, so the input is the engine's, not a player's.
    Low reachability; needs a zod 4 move.
  - `fastify` 5.12.5 (header schema bypass) and `fast-uri` through ajv: no
    route declares a schema, so not reachable. `glob` and `minimatch`
    through `@fastify/static`: patterns are fixed at startup, not reachable.
- Proposed fix: upgrade the MCP SDK to 1.32.0 or later and fastify to
  5.12.6 or later in their own changes, rerun the engine-client contract
  tests against a live engine and play a game; plan the zod 4 move.
- Status: open.
