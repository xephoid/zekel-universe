## What changed

- **F13 (per-client limits behind a proxy).** New opt-in `CLIENT_IP_HEADER`
  (empty by default). When set, the guest and sign-in-link limiters key on
  that header if it holds exactly one valid IP address; otherwise they use
  the peer address. `trustProxy` stays off, so `X-Forwarded-For` is never
  read. The setting must be one plain header name; `x-forwarded-for`,
  `forwarded` and `x-real-ip` are refused at startup. `render.yaml` sets
  `cf-connecting-ip`.
- **Assumption:** this trusts that every request reaches the service through
  Render's edge (Cloudflare), which overwrites `CF-Connecting-IP`. Render's
  own articles say so; it is not testable without a deployment. If a request
  could reach the container another way, its caller could choose their
  budget key. Recheck on staging.
- **`/healthz`.** Answers `{"ok":true}` when the database answers a
  `select 1`, else 503 `{"ok":false}`; `no-store`; does not call the engine;
  reveals nothing else.
- **`ENGINE_HOSTPORT`.** The server builds `http://<host:port>/mcp` from it
  when `ENGINE_URL` is unset, so the Blueprint can pass the engine's private
  address. Validated as `host:port`. The engine link is plain HTTP on
  Render's private network (the existing P3 note on `http://` engine URLs
  applies).
- **`render.yaml`.** Public web service (Docker, `/healthz`), private engine
  service (`pserv`, built from `xephoid/zekel-games` `main`, SQLite sessions on
  a 1 GB disk, one instance), Render Postgres with `ipAllowList: []`.
  `SECRET_KEY` and `MCP_BEARER_TOKEN` are `generateValue`; `ENGINE_TOKEN`
  copies the engine's token by `fromService.envVarKey`; `APP_ORIGIN`,
  `RESEND_API_KEY` and `EMAIL_FROM` are `sync: false`. Both services have
  `autoDeployTrigger: "off"` while CI is off. No secret value in the file.
