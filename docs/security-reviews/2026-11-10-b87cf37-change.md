## What changed

- **F11 (sign-in link bound to the browser).** `POST /api/auth/email/link`
  sets a random 32-byte nonce in a cookie (`universe_signin`; `__Host-`
  prefixed and `Secure` when cookies are secure; `HttpOnly`, `SameSite=Lax`,
  `Path=/`, 15 minutes). The link row stores the nonce's SHA-256. Asking
  again from the same browser reuses a well-formed nonce, so an earlier mail
  still works there. `POST /api/auth/email/complete` refuses a request with
  no nonce cookie (401 `sign_in_wrong_browser`) before it looks at the token,
  so the token is not used up and nothing about the browser changes. With a
  nonce, the consuming delete matches on token hash and nonce hash together,
  so a wrong nonce is a plain 401 `invalid_or_expired_token`, and again
  nothing is consumed. On success every pending link for that nonce is
  deleted and the cookie is cleared. The guest-seat merge runs only after
  both checks pass.
- **F11, landing page.** The page posts the token once (also under React's
  double effect run), removes the token from the address bar and history
  entry, and on a 401 says the link works once and only in the browser where
  it was asked for. The request page says to open the link in this browser.
- **F12 (sockets after sign-out and expiry).** The socket handshake keeps the
  credential it read (session token hash or guest id, with its expiry), and
  each socket joins a room for that credential. Sign-out deletes the session,
  ends an unupgraded guest cookie on the server, and disconnects those rooms
  once the reply is sent. Guest upgrade disconnects the guest's room. Every
  incoming socket message checks the credential against the database first;
  a dead one gets an `unauthorized` acknowledgement and the socket is closed,
  and a database error fails closed. A timer (60 s by default,
  `socketRecheckMs`) checks every open socket, so one that only listens stops
  within a minute; a broadcast also skips and closes a socket whose
  credential is past its known expiry. The web client reconnects once after
  a server-side disconnect, so the browser's new cookies decide who it is.
- **Guest expiry.** `guests.expires_at` (schema 6) is set to creation plus
  365 days, the cookie's own lifetime, now enforced by the server. Older rows
  without it expire 365 days after `created_at`. An expired guest reads as
  nobody on REST and sockets and cannot be upgraded into an account.

## Findings

- SEC-03-F11: fixed (see above). Regression: `session-revocation.test.ts`,
  first two tests.
- SEC-04-F12: fixed, including server-side guest expiry. Regression: the
  rest of `session-revocation.test.ts`.
- No new finding. Notes for the owner:
  - A sign-in link now only works in the browser that asked for it. Asking
    on a laptop and opening the mail on a phone is refused with a plain
    message; that is the chosen trade-off.
  - The guest lifetime (365 days, matching the cookie) is a product choice;
    shorter or sliding expiry would change how long guest games survive.
  - A listening-only socket can still receive views for up to the timer
    interval (60 s) after a revocation that did not go through sign-out or
    upgrade (for example, an operator deleting a session row).
