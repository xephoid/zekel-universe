Static serving and fallback:

- `@fastify/static` serves `apps/web/dist` whenever that folder exists, whatever `NODE_ENV` is (1056–1058).
- For any GET not under `/api`, the not-found handler returns `index.html`. Everything else gets a JSON 404.

**Socket.IO**

- Admission: `allowRequest` checks the Origin exactly (a missing Origin is allowed). Then middleware reads the principal from the cookie, once, at the handshake.
- `join_table`: requires a seat; stores the first owned seat per table; replays events after `lastSeenSeq`; marks notifications read; calls `resumeTable`.
- `leave_table`, `move`, `undo`, `disconnect`.
- `query`: 30 per 10 s per connection; name up to 64 characters; args up to 4096 bytes of JSON.
- Server to client: `table_event`, sent per socket through `toWireEvent` with that socket's own seat. `table_status` is defined in shared but never sent.

**Other entry points**

- Timer: `sendDueNudges` every 60 s by default (line 98). It re-checks, when it sends, that the table is in play, the turn is still that person's, and they are not connected.
- Startup: `refreshCatalog`.
- Outbound: the engine over MCP with a bearer token (`packages/engine-client/src/index.ts:472`); Resend at a fixed URL (`email.ts:31`).
- No uploads, no admin routes, no dev-only server routes. The web route `/dev/ngg` sits behind `import.meta.env.DEV` (`apps/web/src/main.tsx:41`), and the built bundle has no `DevNgg` or `dev/ngg` string.

### Production fail-closed runs

Every run used `env -i` with only `PATH`, `SYSTEMROOT`, `PORT=8795` and

### Findings (whole app)

#### SEC-05-F10 — An encoded path gets past the Origin check (and the API no-store header)

- Severity and confidence: P2, reproduced.
- Where: `apps/server/src/app.ts:155–161` (`if (!req.url.startsWith('/api/')) return;`) and `app.ts:171` (the header split).
- What happens: Fastify routes on the decoded path, so `/%61pi/<route>` reaches `/api/<route>`. `req.url` stays raw, so the state-changing request skips `originAllowed`.
- Reproduction:
  - In-process: `POST /%61pi/guests` from Origin `http://evil.example` → 200, and one guest row created.
  - `PATCH /%61pi/me` with a victim's cookie and a hostile Origin → 200, and the name was changed to a marker. Control on `/api/me` → 403.
  - On the built production-mode server: curl `POST /%61pi/guests` from a hostile Origin → 200, including with `content-type: text/plain`.
- Impact:
  - Any cookie-authenticated write (join, ready, start, invites, friends, PATCH `/api/me`, sign-out, delete table) can be forged from any origin whose requests still carry the cookie: a same-site sibling origin, or a browser that does not enforce SameSite=Lax.
  - Body-less routes need no JSON, so a `text/plain` form works.
  - The API answers on these paths also carry no `no-store` header.
- Fix: make the checks independent of how the path is spelled.
  - Apply the Origin check to every non-GET/HEAD/OPTIONS request; static files are GET only.
  - Or test the matched route (`req.routeOptions.url`), or the decoded path.
  - Choose the `no-store` split the same way.
- Regression test: `%61pi` and mixed encodings on POST, PATCH and DELETE → 403 with no rows written.

#### SEC-03-F11 — A sign-in link is not tied to the browser that asked for it; the guest's seats move to the link's account

- Severity and confidence: P2 (high end), reproduced.
  - It meets the playbook's P1 wording (unauthorized seat access and game writes), but it needs the victim to open a link the attacker sends. The user should decide.
- Where: `app.ts:282–325`; `apps/web/src/pages/SignIn.tsx:67` (the landing page posts the token automatically on load).
- What happens:
  1. The attacker requests a link to their own address and passes the URL to a victim (a genuine app URL).
  2. The victim's browser posts the token along with its guest cookie.
  3. The server signs the browser in as the attacker and moves the victim's seats, hosted tables and notifications to the attacker's account.
- Reproduction (harness T4): completion → 200 with the attacker's `userId`; the attacker's own later session has `mySeats` [1] at the victim's table; the victim's guest cookie is now nobody.
- Impact: the attacker reads that seat's private views and moves for it. The victim also plays on inside the attacker's account (classic login CSRF).
- Fix, any of:
  - Bind the link to the requesting browser: a random nonce in a cookie set by `/api/auth/email/link`, required at `/complete`.
  - Or show a confirm step ("Sign in as a…@…?") that names the account.
  - Or never merge guest seats unless the same browser started the flow.
- Regression test: completion from a browser without the start cookie → refused, and no seats move.

#### SEC-04-F12 — Sign-out and expiry do not reach open sockets

- Severity and confidence: P2, reproduced.
- Where: `app.ts:929–938` (the principal is read once, at the handshake); `app.ts:327` (sign-out deletes the session but disconnects nothing).
- What happens: T5 signed in, opened a socket and joined a table against the AI, then signed out.
  - REST with the old cookie → 401, and a new socket → refused.
  - The old socket's `move` → ack ok, and the engine recorded the move.
  - The same holds when a session expires: nothing rechecks it.
- Impact: a stolen session's live socket survives sign-out and revocation; a shared computer stays usable from another tab.
- Also: guest tokens never expire on the server (P3).
- Fix:
  - Recheck the principal in each handler (or on a short timer), and disconnect sockets whose session is gone.
  - Keep a principal→sockets map so sign-out and upgrade disconnect them.
  - Give guests a server-side expiry.

#### SEC-16-F13 — The per-IP limits collapse into one shared budget behind a proxy

- Severity and confidence: P2, source-confirmed. That Heroku's router appears as the peer address is documented platform behaviour, not tested here.
- Where: `app.ts:214, 268` (`req.ip`); no `trustProxy` in `buildApp`. The tests assume `X-Forwarded-For` is ignored (`hardening.test.ts:130`, `rest.test.ts:489`).
- Impact on the planned Heroku deploy (Procfile): every visitor shares 30 guests and 30 sign-in link addresses per 15 minutes. One script blocks guest play and sign-in for everyone.
- Fix: set `trustProxy` to the deployment's hop count (Heroku: 1), only when the app is deployed behind it, and keep the default locally. Add a test for the proxied key.

#### P3s (new)

- **SEC-09-F14, join race.** `tables/service.ts:313–318` reads an open seat, then updates it with no `user_id IS NULL AND guest_id IS NULL` condition. Two concurrent joiners both get 200 for seat 1, and the first silently loses it (T2). Fix: a conditional update, then check the affected-row count and retry.
- **SEC-10-F15, wrong types give 500.** Nine routes call `.trim()` or `.slice()` on fields that are not strings (T6). No mutation, generic body, but each is logged as a server error. Fix: `typeof` checks, or Fastify JSON schemas.
- **SEC-14-F16, known development key accepted.** `config.ts:74` checks only that the key is present. Fix: refuse the development key (and short keys) in production, and add a test in `auth.test.ts`.
- **SEC-14-F17, GCM tag length not pinned.** `crypto.ts:28–31` does not pin `authTagLength: 16` or check the buffer length (Node `DEP0182`). There is also no AAD binding the ciphertext to its table id. Exploiting either needs write access to the DB.
- **SEC-17-F18, no security event log.** Nothing records authorization failures, rate-limit hits, origin rejections or revoked-session use. There is no incident or revocation runbook.
- **SEC-11-F19, CSP and HSTS.** `connect-src 'self' ws: wss:` allows sockets to any host; narrow it to `'self'` (same-origin ws is covered by `'self'` in current browsers). The app sets no HSTS; set it in production, or verify the proxy sets it.
- **SEC-18-F20, CI.** No `permissions: contents: read`. `xephoid/zekel` is checked out at its default-branch HEAD, so CI runs whatever that repo's main holds. The dev-tool advisories are in the table above.
- **Hypothesis (P3): the sign-in `next` value.** It is accepted when it starts with `/`, which includes `//host`. `SignIn.tsx:81` passes it to react-router `navigate`. I have not shown this to be an open redirect (pushState refuses a cross-origin URL); tightening it to `/^\/(?!\/)/` is cheap.
- **Disclosure nit, fixed in this commit.** An earlier report listed a local account name among its search terms; the word is now "the local account name".
