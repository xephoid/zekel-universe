## What changed

- **The server runs Supabase's PKCE flow.** `POST /api/auth/supabase/start`
  makes the PKCE secret, keeps it in an HttpOnly cookie (`universe_oauth`,
  ten minutes, never cleared, only left to expire or replaced) and answers
  with Supabase's authorize address, which carries only the secret's hash. `POST /api/auth/supabase/complete` takes the
  one-time code, trades it with that cookie's secret, checks the access
  token, signs the player in with Universe's own cookie, ends the Supabase
  session and drops the tokens. No Supabase token reaches the browser.
- Completion is safe to repeat: the session's cookie value is an HMAC of the
  code and this browser's secret under the server's key, so sending the same
  code again from the same browser returns the same session, without asking
  Supabase. That is how a lost answer is recovered.
- Other route: `GET /api/auth/providers` (the buttons to show).
- New page: `/auth/callback`. It sends the code to the server, then loads
  the next page afresh.
- The end of a sign-in moved from the email route into `finishSignIn`,
  shared by both. No behaviour change: the existing sign-in and revocation
  tests pass unchanged.
- New settings: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, server only, both
  or neither, https only (local http allowed for Supabase's local stack).
- New dependency: `jose` 6.2.12 (server). The web app has no new dependency.
- No database change. No change to the page's security policy.

## Findings

All fourteen are fixed. F01, F03 and F05 are closed by the redesign (the
server runs the flow); F08 and F11 to F13 by making the completion safe to
repeat; the rest by direct fixes. F06 to F10 came from the third Codex
pass, F11 to F14 from the fourth.

### SEC-03-F01 — A Supabase token could sign in more than once, or for someone else

- Severity: high. Found by this review (first rated medium) and widened by
  both Codex passes.
- What was wrong: in the first version the browser held Supabase's access
  and refresh tokens and sent the access token to the server. The same token
  could sign in again until it was five minutes old; two posts at once could
  both succeed; anyone who copied a fresh token could make a lasting
  Universe session; and with the refresh token a later token for the same
  Supabase session could be made. Two partial fixes (ending the Supabase
  session; a table of used Supabase sessions plus a cookie) narrowed this
  but did not tie the token to the browser that started the sign-in.
- Fix: the server runs the PKCE flow. The secret lives only in that
  browser's HttpOnly cookie, Supabase trades a code once and only with that
  secret, and the tokens never leave the server, which ends the session at
  once. The table and the browser library are removed.
- Tests: "a code is useless anywhere but the browser that started its
  sign-in, and only once" (five cases).

### SEC-04-F02 — The browser's clean-up signed the player out of Supabase everywhere

- Severity: medium. Found by Codex.
- What was wrong: the first version's browser called Supabase's
  `signOut()`, whose default ends all of the user's Supabase sessions.
- Fix: first `scope: 'local'`; now the browser holds no Supabase session at
  all, and the server ends only the one it made (`/logout?scope=local`).

### SEC-04-F03 — A sign-in that worked could be shown as failed

- Severity: medium. Found by Codex, both passes.
- What was wrong: a lost answer after the server signed the player in
  showed an error, with the code spent.
- Fix: `POST /api/auth/supabase/status`, keyed on the code, as the email
  link has. If even the cookie was lost on the way, the browser holds no
  new session and the player clicks again (O1).
- Tests: "when the answer is lost…" (server), "a lost answer…" (page, two),
  "a refusal is a refusal unless…".

### SEC-04-F04 — After switching accounts the page could keep showing the old one

- Severity: medium. Found by Codex, second pass.
- What was wrong: the page refreshed its account details after signing in,
  and that refresh keeps the old details when it fails.
- Fix: the callback loads the next page afresh. Test: "sends the code once,
  clears the address bar and loads the next page afresh".

### SEC-03-F05 — Tests claimed more than they showed; a shared cookie broke the other sign-in

- Severity: low and medium. Found by Codex.
- What was wrong: the first callback test let any number of identical calls
  pass; and the second version's cookie, shared with the email link, was
  cleared by whichever sign-in finished first, breaking the other.
- Fix: the page test now counts exactly one completion under React's double
  run, and a test of the real module asked twice at once; a separate cookie
  for each kind of sign-in, with a test of both orders.

### SEC-05-F06 — The page after sign-in could be sent to another site

- Severity: medium. Found by Codex, third pass.
- What was wrong: the check (starts with `/`, not `//`) let `/\evil.example`
  through, which browsers read as `//evil.example`.
- Fix: `safeNext` parses the destination against this site and keeps it
  only if the origin is this site's. Test: "where to go after signing in".

### SEC-04-F07 — A failure after the trade was offered as retryable

- Severity: medium. Found by Codex, third pass.
- What was wrong: if Supabase's user lookup failed after the code was
  traded, the server answered "try again", but the code was spent; and
  Supabase's "too many requests" was treated as a dead code.
- Fix: only a trade Supabase did not take (429 or 5xx) is retryable; after
  the trade every failure says "start again". Tests: "when Supabase is down
  or busy at the trade…", "once the code is traded…".

### SEC-04-F08 — A sign-in whose cookie was lost could not be recovered

- Severity: medium. Found by Codex, second and third passes.
- What was wrong: if the completion's whole answer, cookie included, was
  lost, the account was signed in (old session ended, guest moved) but the
  browser had no way back.
- First fix: a resume route that replaced the stranded session. Codex's
  fourth pass found that it brought its own problems (F11 to F13).
- Fix: the completion is safe to repeat (see "What changed"); the page sends
  the code once more when the answer is lost. Tests: "when the answer is
  lost, sending the same code again is safe" (six).

### SEC-04-F09 — An older sign-in could spoil a newer one

- Severity: medium. Found by Codex, third pass.
- What was wrong: the secret cookie was cleared on a refused code, so an
  older sign-in's late return wiped the newer sign-in's secret.
- Fix: the secret is never cleared, only replaced or left to expire. Test:
  "an older sign-in's late return…".

### SEC-04-F11 — The resume route could take over a delivered session and renew its own window

- Severity: medium. Found by Codex, fourth pass.
- What was wrong: resume replaced the matching session even when it had
  been delivered, revoking the one the browser was using, and each
  replacement restarted the ten minutes.
- Fix: no replacement at all. A repeat hands back the same session, and the
  ten minutes count from the original sign-in ("many repeats…").

### SEC-04-F12 — Resume skipped the account-switch rules

- Severity: medium. Found by Codex, fourth pass.
- What was wrong: a resume after the browser had signed in elsewhere, or
  become a new guest, set the old account's cookie without ending the newer
  session or moving the guest.
- Fix: a repeat is refused once the browser has signed in elsewhere or
  become a new guest; the newer session stays ("no once the browser has
  signed in elsewhere…", "…become a new guest").

### SEC-04-F13 — Resumes at once could leave a revoked cookie; a failed save looked retryable

- Severity: medium. Found by Codex, fourth pass.
- What was wrong: two resumes could each replace the session and answer out
  of order; a database failure after the trade answered 500, which the page
  offered to retry though the code was spent.
- Fix: repeats return the same cookie, so order does not matter; a failed
  save answers `sign_in_failed`, and the page offers "Try again" only for
  `sign_in_unavailable` and `too_many_requests`. Tests: "many repeats, even
  at once…", "a failure to save…", "a refusal or a failed save is final…".

### SEC-05-F14 — The address check returned a path that could read as another site

- Severity: medium. Found by Codex, fourth pass.
- What was wrong: `/.//evil.example/x` parses as this site, but its path,
  `//evil.example/x`, is read as another site when navigated to.
- Fix: the full checked address is returned. Test: "a path that only looks
  like another site stays on this one".

### SEC-04-F10 — The email link's cookie was never deleted in production (on `main`)

- Severity: low. Found by Codex, third pass (on the new cookie); the same
  line was already in the email route on `main`.
- What was wrong: a `__Host-` cookie is deleted only by a Set-Cookie with the
  same attributes, Secure among them; the email route's deletion had none,
  so browsers ignored it and the nonce stayed until its 15 minutes ran out.
- Fix: the deletion uses the cookie's own options. Test: "with secure
  cookies…", shown to fail with the old line.

## Limitations and observations

- **L2 — the trust rests on Supabase's configuration.** That the project uses
  asymmetric signing keys (otherwise every sign-in is refused, which fails
  closed), lists only the site's own return addresses, and marks emails
  confirmed only when Discord or Google say so. Checked by hand at setup.
- **O1 — the email landing page, outside this change.** It still refreshes
  the account details in place after signing in rather than reloading (the
  F04 pattern).
