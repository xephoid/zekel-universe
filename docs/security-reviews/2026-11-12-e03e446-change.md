## What changed

- New routes: `GET /api/auth/providers` (public: the Supabase project
  address and its publishable key, or null);
  `POST /api/auth/supabase/start` (sets this browser's sign-in cookie);
  `POST /api/auth/supabase/complete` (takes Supabase's access token, signs
  the player in with Universe's own cookie); `POST /api/auth/supabase/status`
  (did this token's sign-in make this browser's session; changes nothing).
- New page: `/auth/callback`. The sign-in page shows Discord and Google
  buttons only when the server offers them.
- The end of a sign-in (old session ended, guest moved, new session, cookie,
  sockets cut) moved from the email route into `finishSignIn`, shared by both
  routes. No behaviour change: the existing sign-in and revocation tests pass
  unchanged.
- New settings: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, both or neither,
  https only (local http allowed for Supabase's local stack). Unset: nothing
  new is offered.
- New dependencies: `jose` 6.2.12 (server), `@supabase/auth-js` 2.118.0
  (web, loaded only when a sign-in button is used).
- The page's `connect-src` gains the Supabase project address when it is set.
- Database version 9: a new table, `supabase_sign_ins` (hash of a Supabase
  session id, the account, when), so a Supabase session signs in once.
  Identities use the existing `identities` table with provider `supabase`.

## Findings

### SEC-03-F01 — A Supabase token could sign in more than once

- Severity and confidence: high (first recorded here as medium; the
  cross-vendor review showed why that was too low), confirmed by test.
- Affected entry point: `POST /api/auth/supabase/complete`
  ([app.ts](../../apps/server/src/app.ts)).
- Actor and preconditions: someone who obtains a player's Supabase access
  token (from that browser, a proxy log, or a shared device) within five
  minutes of the player signing in, when the browser's own sign-out from
  Supabase did not get through.
- Expected versus observed: a token should sign in once. Before the fix the
  server accepted it again until the five-minute age limit. The first fix
  (`e03e446`, the server ends the Supabase session after use) still let two
  posts at the same moment both succeed, and left the token usable whenever
  Supabase could not be reached to end the session. Each use made a lasting
  Universe session for whoever held the token, not only an extra session for
  the player, as this report first said.
- Reproduction: post the same token twice, one after the other and at once.
- Fix: a Supabase session signs in once. Its id's hash is written to
  `supabase_sign_ins` inside the transaction that makes the Universe session;
  the primary key refuses a second use. The server still ends the Supabase
  session too. Regression tests: "two uses of one token at the same moment
  give one sign-in", "when Supabase cannot end its session, … still signs in
  once only", "a new token from the same Supabase session is refused too".
- Status: fixed.

### SEC-04-F02 — The browser's clean-up signed the player out of Supabase everywhere

- Severity and confidence: medium, confirmed by reading the library's
  default (`signOut()` ends all of the user's sessions).
- Affected entry point: [supabaseSignIn.ts](../../apps/web/src/supabaseSignIn.ts).
- Expected versus observed: ending this sign-in's Supabase session should
  leave the player's other Supabase sessions alone; the default ended them
  all whenever the server had not already ended this one.
- Fix: `signOut({ scope: 'local' })`, its error ignored either way. Test:
  "…then ends Supabase's session" asserts the scope; "a sign-out error from
  Supabase does not undo the sign-in".
- Status: fixed.

### SEC-04-F03 — A sign-in that worked could be shown as failed, with no way back

- Severity and confidence: medium, confirmed by reasoning; now tested.
- Affected entry point: the callback page and
  [supabaseSignIn.ts](../../apps/web/src/supabaseSignIn.ts).
- Expected versus observed: if the completion's answer is lost after the
  server signed the player in, the page should find that out; it showed an
  error, and the one-time code was spent. A failed refresh of the account
  details afterwards also showed an error.
- Fix: `POST /api/auth/supabase/status`, as the email link's landing page
  has. Each session records which Supabase session made it; the route checks
  the token's signature only (its Supabase session may be ended) and answers
  yes only for this browser's session. A failed refresh after success moves
  on. Tests: "when the answer is lost…" (server), "a lost answer…" and "a
  failed refresh…" (page).
- Status: fixed.

### SEC-03-F04 — Tests claimed more than they showed

- Severity and confidence: low, confirmed.
- Expected versus observed: the callback test compared a set of calls, so
  any number of identical calls passed; the PKCE test checks the library's
  settings, not that a second browser is refused.
- Fix: a test of the real code asked twice at the same moment ("trades a
  code once…", shown to fail with the guard removed); the page test bounds
  the call count; this report says what the PKCE test does and does not
  show, and keeps the real check under "blocked".
- Status: fixed.

## Limitations

- **L1 — closed.** Recorded in this report's first version as an accepted
  limit (simultaneous use and a failed logout); fixed under F01.
- **L2 — the trust rests on Supabase's configuration.** That the project uses
  asymmetric signing keys (otherwise there are no public keys and every
  sign-in is refused, which fails closed), lists only the site's own return
  addresses, and confirms emails only when Discord or Google say so. These
  are settings in Supabase, checked by hand at setup.
