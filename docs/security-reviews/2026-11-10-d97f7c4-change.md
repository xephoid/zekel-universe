## Findings

### SEC-04-F27 — Signing in as another account left the old session's sockets working

- Severity and confidence: high; reproduced.
- Affected entry point: `POST /api/auth/email/complete` in [app.ts](../../apps/server/src/app.ts).
- Actor, preconditions, and violated boundary: a person signed in as A completes a link for B in the same browser. The new cookie replaced A's, but A's session stayed valid in the database, so the browser's shared socket kept acting as A and receiving A's views; signing out of B never ended A.
- Fix: completing a sign-in deletes the session the request carried and disconnects that session's sockets after the reply, so they reconnect with the new cookie. Only the requesting browser's own session is touched; nothing moves to the new account. A refused completion changes nothing.
- Regression: `session-revocation.test.ts`, "signing in as another account …", "signing in again as the same account …", "a refused completion …". Both new tests failed before the fix.
- Status: fixed.

### SEC-08-F28 — A socket could join its credential room after the room was disconnected

- Severity and confidence: high in design; reproduced as a stale connection, a leaked presence mark, and (with an asynchronous room join) delivery of events to a signed-out socket.
- Affected entry point: Socket.IO handshake, connection and `join_table` in [app.ts](../../apps/server/src/app.ts).
- Expected versus observed: a socket whose credential was read before sign-out stayed connected until its next message or the timer; with an asynchronous room join it could join a table and hear broadcasts; a sign-out during `join_table` left the account marked present and a stale room member.
- Fix: the connection joins its credential room and then reads the credential again; no message is handled until that passes, and a failed check cuts the socket. `join_table` subscribes, checks again, and only then records the seat (broadcasts go only to sockets with a seat and a passed check), marks presence and replays. Fails closed on a database error.
- Regression: three paused-boundary tests in `session-revocation.test.ts`; all three failed before the fix.
- Status: fixed.

### SEC-03-F29 — A sign-in link was lost when its post failed before the server answered

- Severity and confidence: medium (availability); reproduced in jsdom.
- Affected entry point: the sign-in landing page, [SignIn.tsx](../../apps/web/src/pages/SignIn.tsx).
- Fix: the token leaves the address bar at once but stays in page memory; no answer or a server error offers Try again. Before calling anything a failure, the page asks `/api/me` whether this browser is now signed in as someone it was not before; if so it moves on. A refusal (4xx) ends with the plain message and no Try again. The in-flight exchange is keyed by its token, so a later link never reuses an earlier one.
- Regression: five new tests in `sign-in.test.tsx`; the three retry and lost-answer tests failed before the fix.
- Residual: if the server finished but the browser never stored the cookie, the link is spent and a new one is needed. If the account was already signed in before and the first check of who was signed in failed, a refused retry can be read as success; that only navigates as the account already present.
- Status: fixed.
